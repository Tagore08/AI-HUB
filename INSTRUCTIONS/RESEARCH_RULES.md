# Research Rules

**Last reviewed**: 2026-10-03  
**Scope**: Information gathering, technical documentation review, and evidence synthesis.

---

## 1. Primary Source Mandate

- **Direct Evidence Over Summaries**: Always prioritize primary artifacts (official documentation, vendor source code, raw specification RFCs, or verified runtime output) over blogs, secondary summaries, or forum discussions.
- **Verification Requirement**: Never cite an API, function signature, or configuration flag as existing unless verified against official documentation, actual code, or command-line testing.
- **Marking Unknowns**: If documentation is missing, contradictory, or inaccessible, explicitly mark the item as `UNKNOWN`. Never fabricate or infer details to present a complete-looking answer.

---

## 2. Citation and Provenance

- **Specific Attribution**: Provide exact URLs, file paths, and line numbers for all factual claims where possible.
- **Date Awareness**: Technical ecosystems evolve rapidly. Always check and report the publication or release date of reference documentation. Flag potentially outdated information (e.g., deprecated APIs).
- **Distinguish Opinions from Specifications**: Clearly delineate official architectural constraints from opinionated community best practices or informal recommendations.

---

## 3. Synthesis & Evaluation Discipline

- **Balanced Alternative Analysis**: When evaluating architectural patterns, libraries, or methodologies, present objective trade-offs (pros, cons, operational complexity, security posture) rather than declaring one-sided superiority.
- **No Hallucinated Citations**: Never fabricate paper titles, author names, benchmarks, or web links. If a paper or link cannot be directly verified, state that the citation could not be confirmed.
- **Handling Restricted Material**: If documentation is behind a paywall, registration wall, or login page, do not attempt to bypass access controls or make assumptions regarding content. Record the limitation and move to accessible alternatives.
